# Red team: failure modes of the UI redesign plan

Date: 2026-11-20 (UTC). Perspective: Failure Mode Analyst (Murphy's Law). Role: Flow Tracer.
Scope: plan.md and phase-01 to phase-08 in plans/261120-0528-ui-redesign/, checked against the repository at commit 0b73e59 on feat/ui-redesign.

## Finding 1: Per-tab back stacks can never hold history, so the riskiest part of phase 3 adds risk and delivers no behaviour
- **Severity:** High
- **Location:** Phase 3, sections "Key Insights", "Requirements", "Implementation Steps" (steps 2, 5, 8) and "Risk Assessment"; plan.md "Quyết định đã chốt" (defaults)
- **Flaw:** The plan shows the bar only on the four tab roots ("Thanh chỉ hiện ở bốn màn gốc"). That means the user can change tabs only while standing on a root. Every other way to reach a tab also starts on the Home root: the Home tiles and the "You owe" line (phase 4), and the existing Home buttons. App Links and notices never arrive in the running activity. Notices start a new task (NEW_TASK|CLEAR_TASK), and the launch mode is the default with no onNewIntent, so a browser link starts a new MainActivity. As a result, a tab's stack is always exactly [root] at the moment the user leaves it. The behaviours phase 3 promises and tests can therefore never happen through the UI: "lịch sử từng tab còn sau khi chuyển", "bấm lại tab đang mở thì về màn gốc", and "SettingsKey mở từ Home và từ Groups cùng lúc". Meanwhile the plan still takes on the costs: it copies the nav3-recipes 1.2.0 tag, which the research says targets lifecycle-viewmodel 2.11.0, while the repo stays on lifecycle 2.10.0. It also carries an unproven duplicate-key fallback ("chuyển sang tab đó") that contradicts its own requirement ("SettingsKey... được đẩy lên ngăn xếp của tab đang đứng"). And `remove(key)` "searches the stacks" without saying which copy it removes.
- **Failure scenario:** The step-8 tests for history kept across a tab switch and for two simultaneous copies of SettingsKey can only be written by calling `Navigator` directly. They pass, and they prove nothing a user can reach. When the recipe code does not compile against lifecycle 2.10.0, or the per-stack `rememberViewModelStoreNavEntryDecorator` shares one ViewModelStore per contentKey, the fix the plan points to is lifecycle 2.11 plus an AGP bump. The plan puts that behind owner approval, so phase 3 stalls. Phases 4, 5 and 6 all block on phase 3. The only behaviour users would notice ("back from a tab root goes to Home, then exits") needs none of this.
- **Evidence:** Plan phase 3: "Thanh chỉ hiện ở bốn màn gốc", "Bấm lại tab đang mở đưa tab về màn gốc", "`SettingsKey`, `ProKey`, `PaymentMethodsKey` được đẩy lên ngăn xếp của tab đang đứng", and Risk: "giữ một bản cho mỗi khóa, tức nếu khóa đã có ở ngăn xếp khác thì chuyển sang tab đó". Cross-tab entry points exist only on Home: `app/src/main/java/com/dantech/splitvibe/ui/AppNavHost.kt:216-218`, `app/src/main/java/com/dantech/splitvibe/ui/home/HomeScreen.kt:112-115`. The other opens of GroupsKey and RequestsKey come only from links (`AppNavHost.kt:174-177`). Notices start a fresh task: `app/src/main/java/com/dantech/splitvibe/notifications/Notices.kt:73`. Default launch mode and no onNewIntent: `app/src/main/AndroidManifest.xml:40-43`; links are read only in onCreate: `app/src/main/java/com/dantech/splitvibe/MainActivity.kt:46-47`. Version mismatch: `gradle/libs.versions.toml:10-11` (lifecycle 2.10.0, navigation3 1.2.1) against research/researcher-01-navigation3-bottom-bar.md:30 ("The `1.2.0` tag ... targets Nav3 1.2.0 and lifecycle-viewmodel 2.11.0") and :68 (the separate-state overload exists only from 2.11).
- **Suggested fix:** Decide with the owner before phase 3 starts. Either (a) show the bar on tab detail screens too, so that per-tab history exists and the multi-stack model is earned, or (b) keep one stack and give tab switches "replace root" semantics, with back from a root going to Home. If (a) is chosen, pin the recipe to code that compiles on lifecycle 2.10. Choose one rule for duplicate keys and state it as a requirement rather than as a fallback. Write the tests through the UI (clicks on the bar), not through `Navigator`.

## Finding 3: The per-phase test gate is undefined, contradicts itself, and nothing runs CI on the branch for 25 days
- **Severity:** High
- **Location:** Success Criteria of phases 1 to 6 ("qua khi bỏ các bài so ảnh"); Phase 3, "Risk Assessment" (the 14-back-swipe-preview guard); Phase 7, step 1; Phase 8, step 8; plan.md decision "Ảnh tham chiếu chỉ được ghi lại và commit một lần ở giai đoạn 7"
- **Flaw:**
  1. No phase says how to "skip the screenshot comparisons". The default mode is `verify`, so `:app:testProdDebugUnitTest` fails every gallery test. Excluding the gallery classes also drops the behaviour checks inside them, such as the scrolls to nodes and the wait for "Payment code for VietQR".
  2. `BackNavigationTest`, which phase 3 requires to pass, captures a screenshot in the middle of its behaviour test. In verify mode it fails at that line in every phase from 1 onwards.
  3. The phase 3 risk "ảnh `14-back-swipe-preview` bắt lỗi này" never fires. Screenshots are not compared until phase 7, and phase 7 step 1 records all of them again in record mode, which accepts whatever is drawn.
  4. `ci.yml` runs only on pull requests and on pushes to main, and phase 8 opens a PR only "khi chủ sản phẩm yêu cầu". Unit tests, lint, the release-package checks and the "No Anthropic code" scan therefore never run on CI for phases 1 to 7. Only device-tests.yml runs on branch pushes, and it runs none of those.
- **Failure scenario:** Phase 1 changes every colour, so all 97 reference images mismatch. Workers then either pass `--tests` filters (the behaviour checks in the galleries are lost) or run in record mode and revert the folder. Phase 1 step 8 does exactly that with "trả cây làm việc về trạng thái đã commit", which removes changed files but leaves any new untracked images that phases 4 to 6 later create under new names. Those images get committed by accident. Phase 3 loses the SPLIT_SURFACE grow animation, and the only automated guard is re-recorded over in phase 7. Problems that local runs miss, such as release minification or the release checks, surface only after merge, where the plan expects CI on main to be green.
- **Evidence:** `app/build.gradle.kts:178-181` (`getOrElse("verify")`); `app/src/test/java/com/dantech/splitvibe/BackNavigationTest.kt:90` (`captureScreenRoboImage(File("src/test/screenshots/14-back-swipe-preview.png"))` inside the behaviour test); `.github/workflows/ci.yml:8-12` (triggers) and `:44-46` ("The unit tests include the screenshot comparison"); `.github/workflows/device-tests.yml:26-35` (push paths: device tests only). Plan phase-03 Success Criteria: "`./gradlew :app:testProdDebugUnitTest` qua khi bỏ các bài so ảnh, gồm ... `BackNavigationTest`".
- **Suggested fix:** Define the gate exactly. For example, run `-Pscreenshots=compare`, which runs every assertion and fails nothing on pixels, and commit nothing under `app/src/test/screenshots`. Add `git clean` for that folder to the revert step. Open a draft PR from phase 1 onwards so that `ci.yml` runs on every push. If the owner forbids PRs, run all `ci.yml` commands locally at the end of every phase, not only in phase 8. Replace the screenshot guard for the grow animation with an assertion: a node that carries SPLIT_SURFACE exists in both scenes during the transition.

## Finding 4: Home's main block reads a cache of requests that only the Requests screen fills, so Home shows the wrong state
- **Severity:** High
- **Location:** Phase 4, "Key Insights" (three sources), "Requirements" (Trang chủ), step 2
- **Flaw:** `HomeViewModel` is meant to combine `RequestRepository.requests`. That flow is a cache, documented as "null before they were ever fetched", and the cache is cleared on every sign-in, sign-out and account deletion, as the plan itself notes. The only caller that refreshes the list is `RequestsViewModel`, created when the Requests screen is composed. The plan has `HomeViewModel` trigger no refresh, and it does not separate "never fetched" (null) from "no requests" (empty). Its rule "Khi chưa đăng nhập hoặc chưa có yêu cầu nào: khối chính hiện chi tiêu" treats both the same.
- **Failure scenario:** The user signs in, which clears the cache, and returns to Home. The main block shows this month's spending and no "Friends owe you", even though the server holds open requests. The numbers appear only after the user opens the Requests tab, after which Home suddenly changes. After a cold start, Home shows whatever list was last fetched, possibly days old, with totals that already include settled requests. The phase-5 criterion "tổng 'Friends owe you' trên màn Requests bằng tổng trên trang chủ" holds only after a visit to Requests.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/data/requests/RequestRepository.kt:53-60` (cache flow, nullable, refreshed by `refresh()`); `app/src/main/java/com/dantech/splitvibe/ui/requests/RequestsViewModel.kt:59-65` (the only refresh, on sign-in inside this view model). Plan phase-04: "Số liệu mới cần ba nguồn: `RequestRepository.requests`, ..." and "Yêu cầu trả tiền bị xóa khỏi máy mỗi lần đăng nhập, đăng xuất và xóa tài khoản".
- **Suggested fix:** Have `HomeViewModel` call `RequestRepository.refresh()` when it starts and when the user signs in, sharing the logic with `RequestsViewModel` rather than copying it. Add a third state for null ("loading" or a stale marker), separate from empty. Add `HomeSummaryTest` cases for null against empty.

## Finding 5: The floating bars hide content and the keyboard, and the tests the plan names cannot detect it
- **Severity:** Medium
- **Location:** Phase 2, "Risk Assessment" (first bullet); Phase 3, "Requirements" (bottom inset); Phase 4, "Risk Assessment" (third bullet) and "Requirements" (result screen with inline inputs, editor with four inputs per open row)
- **Flaw:** The plan claims "các bài kiểm thử cuộn của giai đoạn 4 đến 6 bắt lỗi này" and "bài `BillSafetyTest` cuộn tới 'Paid by' bắt lỗi này". `performScrollToNode` scrolls until the node is inside the scrolling container's viewport. A sibling drawn on top, such as a floating bar in a Box, does not change that, and the test then only counts texts, so occlusion is invisible to it. Today `SvBottomBar` sits in `Scaffold(bottomBar = ...)`, so the Scaffold pads the content. A bar that "floats" with a 20 dp margin and a shadow has to let the content draw beneath it, which removes that padding. Nothing in the plan covers the keyboard. The result screen and the editor use `imePadding()` on the Scaffold, so the bar, now about 96 dp tall including its margins, rides on top of the keyboard. Meanwhile the focused inline field (share, percent or amount, as phase 4 requires) is brought into view only within the list's viewport, which lies underneath the bar.
- **Failure scenario:** On a 5.5-inch phone with 200% text, the user taps the amount field in the last person row. The keyboard opens, the bar sits above it, and the field the user is typing into is hidden behind the bar. The last rows ("Paid by", the extra charges) can never scroll clear of the bar. `BillSafetyTest` and the `ScreenGalleryTest` scroll constants still pass.
- **Evidence:** `app/src/test/java/com/dantech/splitvibe/ui/split/BillSafetyTest.kt:130-132` (only `performScrollToNode(hasText("Paid by"))` and `assertCountEquals(2)`); `app/src/main/java/com/dantech/splitvibe/ui/split/ResultContent.kt:156-158` (`Scaffold(modifier = Modifier.imePadding(), ...)`) and `:174` (`bottomBar = { FinishBar(...) }`); `app/src/main/java/com/dantech/splitvibe/ui/editor/BillEditorContent.kt:72` (`imePadding`); `core/designsystem/src/main/java/com/dantech/splitvibe/designsystem/components/SvPrimaryButton.kt:46-58` (current full-width bar with `navigationBarsPadding`).
- **Suggested fix:** Make it a requirement in phase 2: the floating `SvBottomBar` and `SvNavBar` expose their height as content padding (bottom `contentPadding` on the LazyColumn), and the action bar is hidden or collapsed while the IME is visible. Add a real test: after scrolling to the last node, assert that its bounds lie above the bar's top in root coordinates. Add one device test that types into an inline field with the keyboard up.

## Finding 6: Phase 1 silently changes the web pages' typography, the web review runs against tokens that can still change, and the deploy is coupled to an unrelated release step
- **Severity:** Medium
- **Location:** Phase 1, step 6; Phase 8, "Context", "Key Insights", "Requirements" and "Risk Assessment"; plan.md "Thứ tự và phụ thuộc" ("phần web của nó làm song song được với 4 đến 6") and "Ngoài phạm vi" ("bố cục các trang web")

Phase 1 changes `displaySmall`, `headlineSmall` and `titleLarge` to 800 weight with tighter line heights tuned for Bricolage. The web keeps system-ui, so after `-PwebTokens=write` the web headings become 800-weight system-ui at Bricolage line heights. Both phase 8 ("Bố cục và chữ của trang không đổi") and the out-of-scope rule are broken. Phase 8 looks only at colour roles ("lập bảng vai màu"). The plan also lets the web work run in parallel with phases 4 to 6 "vì `tokens.css` đã được ghi lại ở giai đoạn 1", yet phase 1 says the test decides the final colour values, and phase 7 step 4 fixes contrast "trong token". The web review then checks tokens that later change. Playwright and the 150 KB budget are not in CI. In release.yml, the Worker deploy runs as its own job right after the bundle, in parallel with the upload to Play internal testing.
- **Failure scenario:** People who receive a link see `/s/` and `/r/` headings in heavy system-ui. Vietnamese names with stacked marks (for example "QUÁN ỐC") clip at a 36 px line height. No automated check notices. In phase 7 a contrast fix changes `primary`. `WebTokensTest` then fails in the next run, `tokens.css` is written again, and the six web screenshots the owner already approved are stale. The first release tag after merge, even one cut to hotfix the proxy, deploys the new web pages while users are still on the old app during the Play rollout.
- **Evidence:** `core/designsystem/src/test/java/com/dantech/splitvibe/designsystem/tokens/WebTokensTest.kt:42-49` (system font plus the per-style size, line-height, weight and tracking variables) and `:126-134` (display, headline and title styles exported); `web/src/app.css:70-87` (uses `--sv-type-display-small-*`, `--sv-type-headline-small-*` and `--sv-type-title-large-*`); `.github/workflows/release.yml:286` (the Worker job `needs: bundle`) and `:358` (`wrangler deploy`), separate from the `play` job at `:360-362`.
- **Suggested fix:** In phase 1 step 6, keep the web type variables from their own table, or export a separate web type scale, so that only colours, shapes and shadows follow the app. Make the phase-8 web review depend on phase 7 step 4 (the token freeze), not on phase 1. Add a phase-8 step that compares `tokens.css` against `main` and lists every changed variable. Record in the final report that the first release after merge also ships the web pages.

## Finding 7: Merging Bills and Recurring through a parameterised HistoryKey breaks the open() guard and the history view model, and relies on a notification path that does not exist
- **Severity:** Medium
- **Location:** Phase 6, "Key Insights", "Requirements" ("Mở từ thông báo hoặc từ hành động 'Repeat' vẫn đưa tới thẻ 'Recurring'"), steps 1 and 2, and "Success Criteria"
- **Flaw:** Step 1 replaces every open of `RecurringKey` with opening `HistoryKey(tab = Recurring)`. The Repeat action is called from inside the Bills screen, which is already `HistoryKey(tab = All)`. `open()` skips a push only when the new key equals the top key, and `HistoryKey(All)` does not equal `HistoryKey(Recurring)`. So the action pushes a second Bills screen, which gets a new contentKey and a new `HistoryViewModel` (scoped to the entry). The search the user typed is lost, and back leads to the same screen again. Step 2 also keeps "thẻ đang mở" across process death in some other place, which creates two sources of truth. In addition, no notification today leads to Recurring: the draft notice maps to `AppLink.OpenBill`, which opens the split screen. The requirement and any test written for it describe a flow that does not exist.
- **Failure scenario:** In "All bills" the user searches "Phở", picks Repeat and confirms. The app shows the Recurring tab with the new item, as the success criterion requires, but on a second copy of the screen. Back shows "All bills" with the search empty, and a second back is needed to reach Home. An implementer who follows the notification requirement adds a new AppLink case or changes `OpenBill`, which is a behaviour change to a public entry point with no approval.
- **Evidence:** `AppNavHost.kt:554-556` (`if (lastOrNull() != key) add(key)`); `AppNavHost.kt:277-296` (the History entry creates `HistoryViewModel` per entry at :280; Repeat calls `backStack.open(RecurringKey)` at :294); `AppNavHost.kt:199-203` (per-entry ViewModelStore decorator). Notification path: `app/src/main/java/com/dantech/splitvibe/ui/AppLink.kt:40-42` (`KIND_DRAFT` maps to `OpenBill`), then `AppNavHost.kt:178` and `AppNavHost.kt:170` (opens `SplitKey`).
- **Suggested fix:** Keep `HistoryKey` a data object, or treat its tab as the initial value only. On Repeat, switch the in-screen tab state (rememberSaveable, set by a callback) instead of navigating. Only Home's entry point should pass an initial tab. Remove "Mở từ thông báo" from the requirement, or state outright that the notice opens the draft bill as it does today.

## Finding 8: The type plan cannot be built as written: two ExtraBold files in one family, emphasized styles left out, and no failure mode for font loading
- **Severity:** Medium
- **Location:** Phase 1, "Requirements" (Chữ), steps 2 and 7, "Risk Assessment"; plan.md defaults ("bảy tệp phông tĩnh")
- **Flaw:**
  1. The `display` family is meant to hold Bricolage ExtraBold 14pt and ExtraBold 96pt, with the 96pt file "cho cỡ từ 40sp". Compose matches fonts by weight and style, never by size. Two `Font` entries with weight 800 and normal style in one `FontFamily` resolve to a single file. So the 96pt cut needs its own family, and then `TypographyTest`'s rule "mọi kiểu `display`, `headline`, `titleLarge` thuộc họ `display`" fails for `displayLarge` and `amountHero`.
  2. Step 2 copies "từng kiểu của `Typography()`" using the 12 sizes listed, but the screens and the amount styles also use the Material 3 Expressive emphasized styles. `amountLarge` and `amountMedium` are derived from `headlineMediumEmphasized` and `titleMediumEmphasized`, and `headlineSmallEmphasized` and `titleLargeEmphasized` are used directly. No requirement sets the family of the emphasized styles, so they stay in the default family and show Roboto on the redesigned screens.
  3. Bundled resource fonts load in blocking mode during the first text layout. The plan's only font risk is about Robolectric, and nothing covers a font that fails to load, for example after a bad subset or a file renamed during shrinking.
- **Failure scenario:** The hero amount draws in the 14pt cut, or else `TypographyTest` is weakened to make it pass. "Ask for the money" (RequestMoneyContent) and the Pro plan titles stay in Roboto while the screens around them use Bricolage. The plan's tests do not catch it, because they check only the listed styles. A broken TTF crashes on the first frame on every API level instead of falling back.
- **Evidence:** `core/designsystem/src/main/java/com/dantech/splitvibe/designsystem/tokens/SvTypography.kt:7` (`internal val SvTypography = Typography()`), `:13` and `:16` (amounts built on the emphasized styles), `:19`; uses of the emphasized styles: `app/src/main/java/com/dantech/splitvibe/ui/split/RequestMoneyContent.kt:125`, `app/src/main/java/com/dantech/splitvibe/ui/paywall/ProScreen.kt:140,161`, `app/src/main/java/com/dantech/splitvibe/ui/home/HomeScreen.kt:163`. Plan phase-01: "Họ `display`: Bricolage Grotesque Bold 700 và ExtraBold 800 (bản 14pt), thêm ExtraBold bản 96pt cho cỡ từ 40sp" and step 7.
- **Suggested fix:** Declare `displayHero` as its own `FontFamily` for the 96pt file and change `TypographyTest` to accept either Bricolage family. List all 30 styles (15 baseline and 15 emphasized) in the type table, and add a test that no style uses `FontFamily.Default`. Add a device test on API 26 that draws each family, and keep the fallback chain explicit.

## Finding 9: The phase 7 device-test and baseline-profile steps cannot produce what the success criteria claim
- **Severity:** Medium
- **Location:** Phase 7, steps 7 and 8, "Success Criteria" ("Lượt `device-tests.yml` trên nhánh có cả bốn mức API xanh"), "Risk Assessment" (third bullet)
- **Flaw:** When device-tests.yml is dispatched with `api-levels=true`, it skips both the Android 14 job and the `profile` job. So one run can never show "cả bốn mức API", and the profile that step 8 wants is not recorded in that run. The API-level matrix has `continue-on-error: true`, so such a run is green even when every journey fails, and "xanh" means nothing. Two more ordering problems: the profile is taken in step 8, yet step 3 (owner fixes), step 4 (contrast fixes), step 9 (manual checks) and phase 8 step 7 (review fixes) all change app code afterwards. And dispatch runs share a concurrency group with push runs on the same ref, with `cancel-in-progress`, so the next push cancels a profile run that was started by hand.
- **Failure scenario:** The implementer dispatches the run with `api-levels=true`, sees a green run and ticks "API 26, 30, 34, 36". API 34 never ran, and a failing journey on API 26 is ignored. The baseline profile is downloaded from an earlier push run (which ran on intermediate code), or from a run that a review-fix push cancelled. The release then ships a stale profile.
- **Evidence:** `.github/workflows/device-tests.yml:53` (`if: ${{ !inputs.api-levels }}` on android-14), `:97` (`if: ${{ !inputs.api-levels && !inputs.release }}` on profile), `:152` (`continue-on-error: true`), `:42-46` (concurrency group by ref, `cancel-in-progress: ${{ !inputs.release }}`); `:26-35` (push trigger, so profile also runs on every branch push).
- **Suggested fix:** Use two separate dispatches: one without `api-levels` (Android 14 plus profile) and one with it. Judge each API-level job on its own result, not the run status. Record the baseline profile as the last app-code change before the PR, after phase 8 step 7. Pause pushes, or check that the profile run's head SHA equals the final app commit.

## Finding 10: The rollback sections claim each phase reverts independently, but later phases build on it
- **Severity:** Medium
- **Location:** "Rollback" in phases 1, 2, 3, 6 and 7
- **Flaw:** Every rollback reads "Hoàn lại các commit của giai đoạn" as if nothing depended on the phase.

  - Phase 2's rollback says "Màn hình chưa đổi bố cục nên không có phụ thuộc ngược", yet its own step 1 ("Nơi phải đổi tham số, sửa luôn các chỗ gọi") and step 6 change screen call sites and `ui/common/InputFields.kt`, and phase 2 creates `CategoryStyle.kt` for phases 4 and 6.
  - Phase 3's revert "đưa app về một ngăn xếp", but by then phases 4 to 6 have rebuilt the four roots around `TabRoot` and replaced `backStack.*` with `navigator.*` calls (FontLicencesKey, HistoryKey(tab), Home wiring).
