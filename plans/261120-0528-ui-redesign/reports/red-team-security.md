# Red-team review: UI redesign plan (Security Adversary, Fact Checker)

Date: 2026-11-20 (UTC). Scope: `plan.md` and `phase-01` to `phase-08` in `plans/261120-0528-ui-redesign/`, checked against the repository at commit `0b73e59`. No code was changed and nothing was compiled or tested; this review only reads files and greps them.

## Finding 1: Font binaries enter the APK with no pinned commit, no recorded hash and no integrity gate
- **Severity:** High
- **Location:** Phase 1, sections "Files to Create / Modify" and "Implementation Steps" step 1-2; research `researcher-02-fonts.md` sections 7 and 8
- **Flaw:** Phase 1 says the seven TTFs come from "nguồn và commit ghim theo mục 7 và 8 của bản tra cứu phông". The research does not pin them. Section 8 lists only six files, with no commit for the upstream Bricolage repository. Section 7 gives a raw URL on `main` (`raw.githubusercontent.com/ateliertriay/bricolage/main/...`). The only commits it names (`84745e5b`, `804e62d8`) are the ones Google Fonts pins for *its* builds, and Google Fonts ships only the variable Bricolage file, which the plan does not use. The seventh file, `bricolage_grotesque_display_extrabold.ttf` (96pt), has no source row anywhere; it appears only as "Unresolved question 1". The research says its copies were fetched "through the proxy" into a temporary scratchpad, and that proxy intercepts TLS. Files in `res/font` are not Gradle dependencies, so `gradle/verification-metadata.xml` never sees them. No step records a SHA-256 or provenance file in the repository.
- **Failure scenario:** Upstream `main` moves, or a font is swapped somewhere in the download path. The implementer commits whatever the current `main` raw URL serves. Every user's device then parses a font of unknown origin in Minikin, HarfBuzz and FreeType, a native parser surface that has had font-parsing CVEs before. Nothing in CI or review can later show which upstream bytes were shipped, so a supply-chain substitution, or simply the wrong optical cut, cannot be detected or reproduced. The OFL also requires the shipped `OFL.txt` to match the font's actual copyright holders, which is unprovable without provenance.
- **Evidence:** Phase 1: "nguồn và commit ghim theo mục 7 và 8 của bản tra cứu phông"; researcher-02-fonts.md section 7: "The raw URLs work, for example `https://raw.githubusercontent.com/ateliertriay/bricolage/main/fonts/ttf/BricolageGrotesque-Bold.ttf`", "This folder is temporary, so download again or pin a commit when implementing"; section 8 table has 6 rows, and "Recommended total (6 files)" in section 6; `gradle/verification-metadata.xml:4-5` (`verify-metadata` true, `verify-signatures` false) covers only resolved Gradle artifacts. `docs/security-threat-model.md:401` claims "Gradle checks every artifact", a guarantee that does not extend to vendored binaries.
- **Suggested fix:** Before Phase 1 step 1, record a provenance table in the repository (for example `core/designsystem/src/main/res/font/SOURCES.md`, or a KDoc block in `SvTypography.kt`). Give each file its upstream repository, full 40-character commit, path and SHA-256. Fetch from the full commit URL, not `main`. Cross-check each hash on a machine outside the intercepting proxy, such as a `checksums.yml`-style GitHub runner step. Add a JVM test that hashes the seven resources against that table. Add the 96pt file's source row, or drop it.

## Finding 2: Navigation 3 bump plans to generate trust-on-first-use checksums in the wrong environment
- **Severity:** Medium
- **Location:** Phase 3, "Implementation Steps" step 1 and "Files to Create / Modify" (`gradle/libs.versions.toml`, `gradle/verification-metadata.xml`); "Risk Assessment" (lifecycle 2.11 / AGP fallback)
- **Flaw:** Step 1 asks the implementer to "tải gói mới và thêm mã băm vào `gradle/verification-metadata.xml` theo quy trình hiện có", and to fall back if "không tải hay không kiểm được gói". The documented process runs `checksums.yml` on a clean GitHub runner, then a human diffs the artifact and commits only "what the version change explains". The plan does not name that workflow, and it does not require the diff to be limited to `androidx.navigation3:*:1.2.2`. Signatures are not verified (`verify-signatures` false), so the hash is pure trust-on-first-use. Generating it inside the agent session means trusting whatever the TLS-intercepting proxy and a filled Gradle cache deliver. It also omits parent POMs and alignment files, which the docs warn makes the next clean machine reject the file. Version 1.2.2 was released 2026-11-18, two days before the plan. The contingency path (lifecycle 2.11.1 plus AGP 9.2) would rewrite a large slice of the file and gets no review rule at all.
- **Failure scenario:** The implementer runs `--write-verification-metadata sha256` locally behind the proxy and commits the regenerated file. Any artifact the proxy or a poisoned cache served is now pinned as trusted. Alternatively the local run misses POM or alignment entries, CI on `main` fails on first resolve, and someone "fixes" it by regenerating again, widening the trusted set without review.
- **Evidence:** `gradle/verification-metadata.xml:4-5`; `docs/architecture.md:609-627` ("works them out on a clean machine ... commit it when the difference is only what the version change explains"; "With a filled cache Gradle skips parent and version-alignment files"); `.github/workflows/checksums.yml:56-73`; `gradle/libs.versions.toml:10-11` (`lifecycle = "2.10.0"`, `navigation3 = "1.2.1"`); `gradle/verification-metadata.xml:1682` (navigation3-runtime 1.2.1); research-01 line 96 (1.2.2 dated 2026-11-18).
- **Suggested fix:** Rewrite step 1: bump the catalog, push, take the `verification-metadata` artifact from `checksums.yml`, and commit it only if `git diff` touches only `androidx.navigation3` 1.2.2 components. Put the same rule in writing for the lifecycle/AGP contingency, and require owner sign-off on that diff.

## Finding 3: "Remove 'Photo stays on this phone'" contradicts "consent text unchanged"; the only match in code is the consent string itself
- **Severity:** High
- **Location:** plan.md "Quyết định đã chốt với chủ sản phẩm" bullets 3-4; Phase 4 "Requirements" ("nội dung màn xin đồng ý không đổi một chữ")
- **Flaw:** plan.md tells the implementer to "Bỏ nhãn 'Photo stays on this phone'" and, two lines later, says the consent screen and privacy policy keep their content. Phase 4 repeats "không đổi một chữ". In the codebase the sentence "The photo stays on this phone." exists only inside the consent string `ai_consent_bill_read`, rendered on `AiConsent.kt:73`. The brainstorm says the owner's request was about a *canvas* label on the new-bill screen, but the plan never says so or scopes the removal to the canvas. The privacy policy relies on that consent screen as the legal basis for sending bill text to Anthropic under Vietnamese law.
- **Failure scenario:** An implementer greps for the label, finds only `strings.xml:117`, and trims the sentence to satisfy plan.md. The consent text shown before the first AI call changes without a privacy or legal review. Consents collected afterwards rest on wording that differs from what the privacy policy and compliance notes describe. Or the implementer stalls on the contradiction mid-phase, while phases 4 to 6 run in parallel.
- **Evidence:** `app/src/main/res/values/strings.xml:117` ("Reading a bill sends the text this phone read from its photo ... The photo stays on this phone."); `app/src/main/java/com/dantech/splitvibe/ui/split/AiConsent.kt:73`; `docs/privacy-policy.md:223` (consent "on the screen the app shows before it first uses the AI"); `plans/reports/brainstorm-261120-0148-ui-redesign.md:68` (label "trên màn hóa đơn mới"); plan.md: "Bỏ nhãn 'Photo stays on this phone' ..." / "Màn xin đồng ý và chính sách quyền riêng tư giữ nguyên nội dung."
- **Suggested fix:** In plan.md and Phase 4, say explicitly that the label exists only on the canvas `NewSplit` board, that the app has no such label, and that `ai_consent_bill_read` must stay byte-for-byte. Add a test that asserts the consent strings are unchanged, for example a golden comparison of the `ai_consent_*` values.

## Finding 4: Removing the only in-app view of the text sent to the AI is done with no recorded trade-off or doc check
- **Severity:** Medium
- **Location:** Phase 4, "Requirements" ("Gỡ phần 'sent to Claude'") and "Implementation Steps" step 5; Phase 8 "Requirements" (docs list)
- **Flaw:** The result screen's "Show what was sent to Claude" panel is the only place a user can see the exact OCR text that left the phone. The privacy policy says that text "can include a shop's name and address, a staff member's name or part of a card number". The owner's decision to drop it stands, but the plan states it only as a UX simplification ("quá kỹ thuật"). It does not record the transparency cost. Phase 8 updates seven docs but never checks `docs/privacy-policy.md`, `docs/compliance.md` or the Play Data safety answers against the new behaviour. The plan also adds "App không được gợi ý rằng việc đọc hóa đơn do một model OCR ở máy chủ làm" but leaves `split_asking_claude` ("Claude is working out the bill…") in place without saying whether it complies.
- **Failure scenario:** A user who wants to check what was disclosed, for example after scanning a receipt with a partial card number, can no longer do so in the app. The compliance file still lists in-app visibility as a user right ("Users can see their groups, requests and links in the app"). No one re-reads it, because no phase owns that check. The compliance gap goes unnoticed until an audit or a data-subject request.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/ui/split/ResultContent.kt:373-393`, `:140`; `app/src/main/res/values/strings.xml:346-347`, `:310`; `docs/privacy-policy.md:56`, `:216`; `docs/compliance.md:60`; brainstorm line 99.
- **Suggested fix:** In Phase 4, record the owner decision together with the trade-off, as `review-audit-self-decision.md` requires for user decisions. In Phase 8, add `docs/privacy-policy.md`, `docs/compliance.md` and `docs/play-console.md` (Data safety) to the read-and-confirm list. Note explicitly that their wording still matches an app that no longer shows the sent text.

## Finding 5: The new home screen puts money owed, debtor names and spending on the launch screen without an exposure model or a defined data source
- **Severity:** High
- **Location:** Phase 4, "Key Insights" and "Requirements" (Trang chủ), "Files to Create / Modify"; Phase 3 "Requirements" (Requests badge)
- **Flaw:**
  - The launch screen now shows the sum and names of people who owe the user, what the user owes, this month's spending and a group balance. A Requests badge appears on every root.
  - The plan does not consider recents-screen thumbnails (no `FLAG_SECURE`, no `setRecentsScreenshotEnabled`), shoulder surfing on open, or the shared-phone case. After sign-out, local bills survive (they are deleted only by a delete-account with phone data), so "spending this month" stays on the first screen anyone opens.
  - The "most recently opened group with saved state" has no source in the codebase. `ProxyCacheDao` only reads by exact key, and nothing records "last opened". Phase 4's file list has no data-layer change, so the implementer will improvise. The obvious improvisations break the data-clearing guarantee: a SharedPreferences or SettingsStore "last group id" is not cleared by `ProxyCache.clear()`, the only thing that runs on sign-in and sign-out.
  - The plan never says whether Home refreshes requests. Without a refresh, the sums are whatever was last cached, with no timestamp shown.
- **Failure scenario:** User A signs out and hands the phone to B. Home immediately shows A's monthly spending. If the last-group pointer was stored in settings, it also shows A's group tile as soon as B's own cache contains a group with the same id, or it keeps A's group id around as a stale pointer. Separately, the Android recents thumbnail shows "Friends owe you ₫1.250.000 · Minh, Lan" to anyone who opens the task switcher. Sums go stale for days if the user never opens Requests.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/data/proxy/ProxyCache.kt:16-19`, `:49-52` (only the cache is emptied on sign-in, sign-out and delete); `app/src/main/java/com/dantech/splitvibe/data/account/AccountRepository.kt:73`, `:80-84`; `app/src/main/java/com/dantech/splitvibe/data/bills/SplitVibeDatabase.kt:183-198` (no list or recency query); `app/src/main/java/com/dantech/splitvibe/data/groups/GroupRepository.kt:32-35` (by-id only); `app/src/main/java/com/dantech/splitvibe/data/settings/SettingsStore.kt:68` (`forgetName`, only on deletion); grep for `FLAG_SECURE|setRecentsScreenshotEnabled` in `app/src/main` finds nothing. Phase 4: "Ô nhóm hiện nhóm mở gần nhất có trạng thái đã lưu" with no file listed for it.
- **Suggested fix:**
  - Define the source explicitly: a `ProxyCacheDao` query over `group:%` keys ordered by the entity timestamp, so it is emptied with the cache. Forbid any pointer outside `ProxyCache`.
  - Specify a refresh on Home start, plus a "last updated" fallback.
  - Add an owner decision on whether the totals are hidden in recents, or behind a tap-to-reveal.
  - Add a HomeViewModel test: sign out, then assert the requests block, the group tile and the badge are empty.

## Finding 6: Per-tab back stacks keep token-bearing screens and their in-memory data alive across sign-out and account switches
- **Severity:** Medium
- **Location:** Phase 3, "Requirements" and "Implementation Steps" steps 2, 6 and 8; Phase 3 "Rollback"
- **Flaw:**
  - Today, leaving a `RequestLinkKey(token)`, `JoinGroupKey(token)` or `GroupKey(id)` screen pops it, which destroys its ViewModel. With one saved stack per tab, those entries now survive indefinitely in a hidden tab and in saved state.
  - `RequestLinkViewModel` keeps the previewed request in memory (payment method, creditor name), and it calls `load()` again whenever *any* account signs in.
  - The plan has no rule for what happens to the four tab stacks on sign-out, sign-in or account deletion. Its tests cover recreate, back and links, but not an account change.
  - `Navigator.remove(root)` is redefined to call `goBack()`. A stale callback such as `onBack = { backStack.remove(RequestsKey) }` fired from a non-current tab would then pop the *current* tab instead.
- **Failure scenario:** A opens a payment-request link (it lands on the Requests tab), switches to Home, signs out in Settings and hands over the phone. B signs in and taps Requests. The hidden `RequestLinkKey` screen re-loads with B's session, and B sees A's request details and the creditor's bank details, with an "Accept" button that takes the request on under B's account. Before the change, the same screen would normally have been popped when A left it.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/ui/AppNavHost.kt:109-122` (token-bearing keys are `@Serializable` and saved), `:510-524`, `:504`; `app/src/main/java/com/dantech/splitvibe/ui/requests/RequestsViewModel.kt:121-145` (`mutableState` holds `request`; `signedIn.filter { it }.onEach { load() }`); `app/src/main/java/com/dantech/splitvibe/MainActivity.kt:46-47`. Phase 3 step 2: "`remove(key)` không bao giờ gỡ khóa gốc: với khóa gốc nó gọi `goBack()`".
- **Suggested fix:**
  - Add a Phase 3 requirement: when `account.session` changes identity or becomes null, reset every tab stack to its root and clear the selected tab back to Home.
  - Add a `NavigatorTest` and `BackNavigationTest` case for this.
  - Make `remove(key)` a no-op when `key` is not on the current tab's stack, instead of mapping it to `goBack()`.

## Finding 7: Moving every text field onto a new `SvTextField` can silently drop autocorrect-off and the length caps on payment and AI inputs
- **Severity:** Medium
- **Location:** Phase 2, "Requirements" (`SvTextField` row), "Files to Create / Modify" (`InputFields.kt`) and "Implementation Steps" step 6
- **Flaw:** Step 6 tells the implementer to move every direct Material text-field call to `Sv…` components (28 call sites in 12 files). `SvTextField` is specified only visually ("viền `outline` bo 16 dp cao 52 dp với nhãn phía trên"). The plan does not require it to pass through `KeyboardOptions` or keep per-field truncation. Today `PaymentMethodSheet.Field` sets `autoCorrectEnabled = false` and caps at `MAX_FIELD`, and other fields cap names, currency and the AI instruction. No test in the Phase 2 list asserts either property.
- **Failure scenario:** The new component hard-codes `KeyboardOptions(capitalization = Sentences)`, or drops `onValueChange` truncation. Bank account numbers, IBANs, UPI IDs and PayPal.Me names then go into the keyboard's learned dictionary and suggestion strip, and possibly a cloud-synced IME dictionary. Over-long values reach the proxy, which refuses them, and the user sees a server error instead of a bounded field.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/ui/payments/PaymentMethodSheet.kt:237-252` (`it.take(MAX_FIELD)`, `autoCorrectEnabled = false`), `:108` (account number field); `app/src/main/java/com/dantech/splitvibe/ui/settings/SettingsScreen.kt:140-154`; `app/src/main/java/com/dantech/splitvibe/ui/split/SplitSheets.kt:94`, `:150`; `app/src/main/java/com/dantech/splitvibe/ui/split/RequestMoneyContent.kt:159`; `app/src/main/java/com/dantech/splitvibe/ui/common/InputFields.kt:36-44`.
- **Suggested fix:** Require `SvTextField` to take `keyboardOptions` and `maxLength` with no defaults that weaken today's values. Add a `ComponentBehaviourTest` case per migrated payment field asserting the `ImeOptions` / autocorrect flag and truncation, for example through `SemanticsProperties.EditableText` after over-long input.

## Finding 8: Store screenshot reselection drops the existing data-vetting rules while the new screens show more personal and payment data
- **Severity:** Medium
- **Location:** Phase 8, "Requirements" (store-listing bullet) and "Implementation Steps" step 6; Phase 5 "Success Criteria" (QR scannable)
- **Flaw:** Step 6 says to pick seven new images "từ ảnh tham chiếu mới" and rewrite the table. It does not carry over the existing pre-publication checks: sample data must be fictional, and `28-bill-link`/`29-bill-link-settling` are excluded for showing a test address and an account number. The new screens are richer in personal data. Home shows debtor names and totals; Group shows per-person balances; Settings shows the signed-in email. The gallery fixtures use a realistic VietQR payload (ACB BIN `970416`, account `257678859`, "DANA NGUYEN"), and Phase 5 explicitly requires the QR to stay scannable by a banking app.
- **Failure scenario:** A redesigned request, request-link or payment-methods screenshot is picked as a "nicer" store image. Play visitors scan a working VietQR code for an account the project does not control, or see `minh.tran@example.com`, or the real Ho Chi Minh City restaurant's address and phone number. These are a store-policy and personal-data problem, and impossible to recall from cached listings.
- **Evidence:** `docs/store-listing.md:111-115`; `app/src/test/java/com/dantech/splitvibe/ui/GroupsGalleryTest.kt:119`, `:135-137`; `app/src/test/java/com/dantech/splitvibe/ui/ClaimGalleryTest.kt:93`; `app/src/test/java/com/dantech/splitvibe/ui/ScreenGalleryTest.kt:509` (`signedInAs = "minh.tran@example.com"`); `web/e2e/share-link.spec.ts:33-34` (same account in a full EMVCo payload). Phase 5: "Mã QR trên màn yêu cầu vẫn quét được bằng app ngân hàng".
- **Suggested fix:** In Phase 8 step 6, keep the existing "Before publishing" and "Left out on purpose" rules verbatim, and add a rule: no screenshot containing a QR code, an email, an account number or the sample bill's address or phone. Alternatively, switch the gallery fixtures to an obviously invalid account (for example `000000000`) before recording, so that no recorded image ever encodes a payable QR.

## Finding 9: Phase 7's device-test and profile step names a workflow input that skips both API 34 and the profile job
- **Severity:** Medium
- **Location:** Phase 7, "Implementation Steps" steps 7-8 and "Success Criteria" ("Lượt `device-tests.yml` trên nhánh có cả bốn mức API xanh")
- **Flaw:** Step 7 dispatches `device-tests.yml` with `api-levels=true` and expects results "của cả bốn mức API". Step 8 then takes the baseline profile "từ việc `profile`". With `api-levels=true`, the workflow runs only the end-to-end matrix on API 26, 30 and 36, with `continue-on-error`. The API 34 job with accessibility checks has `if: !inputs.api-levels`, and the `profile` job has `if: !inputs.api-levels && !inputs.release`. Neither runs.
- **Failure scenario:** The run goes green because the matrix cannot fail it. No API 34 accessibility check ran, and no new baseline profile was produced. The release then ships the committed, stale profile ("a release ships the committed one"), and Phase 7's success criterion is ticked on a run that tested neither gate.
- **Evidence:** `.github/workflows/device-tests.yml:7-10`, `:16-19`, `:53`, `:95-97`, `:146-152`.
- **Suggested fix:** Require two dispatches: one with defaults, for API 34 with accessibility checks plus the `profile` artifact, and one with `api-levels=true`. Change the success criterion to "API 34 job and profile job green; the API 26/30/36 matrix results read and recorded".
