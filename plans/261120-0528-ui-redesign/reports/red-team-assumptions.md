## Finding 1: Home and Requests totals read a request cache that nothing fills when Home opens, and "signed out" looks the same as "not fetched yet"
- **Severity:** High
- **Location:** Phase 4, sections "Key Insights" and "Requirements / Trang chủ"; Phase 3, "Requirements" (the Requests count on the bar); Phase 5, "Success Criteria"
- **Flaw:** The plan assumes Home can sum open requests "theo tiền tệ của máy" from cached data in every account state. But only `RequestsViewModel` refreshes the request cache, and it does so only when the Requests entry is composed. Every sign-in, sign-out and account deletion empties the cache. The flow gives `null` both when nothing was ever fetched and after a clear, so the planned `HomeSummary` cannot tell "signed in, not fetched yet" from "signed out" or "no requests". The plan also needs a "most recently opened group", and nothing records that.
- **Failure scenario:** A user signs in from Settings, which empties the cache, and goes back to Home. `RequestRepository.requests` emits `null`, so Home shows the "no requests" state (this month's spending) even though friends owe them money. The Requests count on the bar stays empty for the same reason. Both stay wrong until the user happens to open the Requests tab. The Phase 5 check ("Friends owe you" on Requests equals the Home total) still passes, because both read the same empty cache. For the group tile, the only timestamp is `ProxyCacheEntity.savedAt`, which is the time of the last write (a refresh or any change), not the time the user opened the group. The DAO also has no query that lists cached groups. Phase 4 lists no change to the data layer, and its Rollback section says no stored data changes.
- **Evidence:** `app/src/main/java/com/dantech/splitvibe/ui/requests/RequestsViewModel.kt:60-66` (the only `repository.refresh()` call for requests, in `init` when signed in); `data/requests/RequestRepository.kt:53-54` ("null before they were ever fetched"); `data/account/AccountRepository.kt:73, 83, 173` (`cache.clear()`); `data/bills/SplitVibeDatabase.kt:180` (`savedAt`) and `:183-198` (DAO: only watch/get/put/remove/clear by key); `data/groups/GroupRepository.kt:30-35`. Plan text: phase-04 line 24, "Số liệu mới cần ba nguồn: `RequestRepository.requests` ..."; line 37, "Ô nhóm hiện nhóm mở gần nhất có trạng thái đã lưu"; phase-03 line 37, "Mục Requests mang số yêu cầu đang chờ".
- **Suggested fix:** Have `HomeViewModel`, or one activity-scoped owner shared by Home, the bar count and Requests, call `RequestRepository.refresh()` when signed in, as `RequestsViewModel` does. Model three states explicitly (signed out, loading or unknown, loaded), and do not let `null` mean "no requests". Either add a "last opened group" record with a DAO query and list the data-layer files and migration impact, or define the tile as "the group most recently changed on this phone".

## Finding 2: Per-tab history cannot be reached, and its key test is false on lifecycle 2.10.0
- **Severity:** High
- **Location:** Phase 3, sections "Key Insights", "Requirements", "Implementation Steps" 2, 5 and 8, and "Risk Assessment"; plan.md, "Mặc định do người lập plan đặt"
- **Flaw:** The bar shows only on the four tab roots, and Group, NewSplit, Settings and the other detail screens have no bar. A user can therefore switch tabs only while the current tab's stack is just its root. Every stack that is not on screen is always `[root]`. Three things follow. "Lịch sử từng tab còn sau khi chuyển" can never be seen. "Bấm lại tab đang mở thì về màn gốc" (`popToRoot`) has nothing to pop. And `SettingsKey` can never sit in two stacks through the UI. Separately, the step 8 test "`SettingsKey` mở từ Home và từ Groups cùng lúc ... mỗi bản giữ trạng thái riêng" is false by construction on the pinned lifecycle. In 2.10.0, `rememberViewModelStoreNavEntryDecorator` takes only the activity's `ViewModelStoreOwner` and gets a single `EntryViewModel` from it with the default key. Stores are keyed by `NavEntry.contentKey`, so per-stack decorators share one map: two `SettingsKey` copies get the same view model, and popping one clears the store of the other while it is still on screen.
- **Failure scenario:** The implementer tries to write the tab-history test in `BackNavigationTest` (Groups, then a group, then Requests, then Groups again). It cannot be driven, because the Group screen has no bar. So either the bar gets added to detail screens, which contradicts the `Group` board and makes the shared-key collision real, or the test turns into a `NavigatorTest` that proves nothing about the UI. Three days of Phase 3 then go into four saved stacks, per-stack decorators and a reselect handler that users never exercise.
- **Evidence:** `javap` of `lifecycle-viewmodel-navigation3-android-2.10.0` `ViewModelStoreNavEntryDecoratorKt`: the only overload is `rememberViewModelStoreNavEntryDecorator(ViewModelStoreOwner, Function0)`, which reads `LocalViewModelStoreOwner`. `getEntryViewModel(ViewModelStore)` calls `ViewModelProvider.create(...)` without a key. `EntryViewModel` has `Map<Object, ViewModelStore> owners`, `viewModelStoreForKey(Object)` and `clearViewModelStoreOwnerForKey(Object)`, and the decorator passes `NavEntry.getContentKey()`. `research/researcher-01-navigation3-bottom-bar.md:68` says the separate-state overload arrived in 2.11.0-beta02 and needs AGP 9.2.0; `gradle/libs.versions.toml:2, 10` pin AGP 9.1.1 and lifecycle 2.10.0. Plan text: phase-03 line 20, "`Group` và `NewSplit` (không có thanh)"; line 37, "Thanh chỉ hiện ở bốn màn gốc"; line 70, "mỗi bản giữ trạng thái riêng".
- **Suggested fix:** Have the product owner choose one of two options. (a) Show the bar on tab detail screens, which makes per-tab history real; then plan the lifecycle 2.11 and AGP 9.2 upgrade, or enforce one copy per key, and delete the "separate state" test. (b) Keep the bar on roots only and replace the multi-stack recipe with one stack plus a "switch root" operation. That removes unreachable state, `popToRoot` and the duplicate-key risk, and cuts Phase 3 effort.

## Finding 3: Collapsing `secondaryContainer` into ink turns 11 raw `FilledTonalButton`s and `SvEmptyState` into primary-weight blocks, and the Phase 2 audit misses them
- **Severity:** High
- **Location:** Phase 1, "Requirements" (role table) and "Risk Assessment"; Phase 2, "Implementation Steps" step 6 and "Todo"
- **Flaw:** In light theme `secondary` and `secondaryContainer` are both `#111114`, and in dark both are `#F4F4F1`. `tertiary` and `tertiaryContainer` are both lime. Any Material component that uses the tonal container now renders as a solid ink slab in light theme and a near-white slab in dark. The Phase 2 audit covers only "ô nhập, công tắc, ô chọn, `AlertDialog`". `ColorTokensTest` only checks text on each role; it cannot find a wrong visual hierarchy.
- **Failure scenario:** On the Requests screen, "Pay" and "Confirm" (`FilledTonalButton`) carry the same weight as the main action. In dark theme, "Got it" on the Group screen and "Share" on the Ask for the money screen become white blocks on a `#0F0F12` page. The empty-state badge circle becomes black in light and white in dark. Each screen phase is told only to "dựng lại" the screen, so a tonal button left in place passes every test and ships.
- **Evidence:** `FilledTonalButton(` at `ui/split/AssistantContent.kt:219`, `ui/split/NewSplitContent.kt:207`, `ui/split/RequestMoneyContent.kt:282`, `ui/claim/ClaimScreen.kt:270, 322`, `ui/settings/SettingsScreen.kt:340`, `ui/home/HomeScreen.kt:147`, `ui/requests/RequestsScreen.kt:161, 170`, `ui/groups/GroupScreen.kt:309, 379`; `core/designsystem/.../components/SvEmptyState.kt:39` (`background(colorScheme.secondaryContainer)`). Plan text: phase-01 line 39, "`secondary`, `secondaryContainer` / chữ trên chúng | `#111114` / `#FFFFFF` | `#F4F4F1` / `#111114`"; phase-02 line 80, "Rà những chỗ màn hình gọi thẳng thành phần Material chưa bọc (ô nhập, công tắc, ô chọn, `AlertDialog`)".
- **Suggested fix:** Add `FilledTonalButton` and every reader of `secondaryContainer` or `tertiaryContainer` to the Phase 2 audit, and route them through `SvQuietButton`. Extend `DesignSystemBoundaryTest` to forbid `FilledTonalButton(` on screens. Or keep `secondaryContainer` as a light neutral tint and use `SvPalette.bar` for ink chips.

## Finding 4: The 200% text criterion cannot be met by the floating bar or by `SvHeroAmount`'s auto-sizing as specified
- **Severity:** High
- **Location:** Phase 2, "Requirements" (`SvNavBar`, `SvHeroAmount`) and "Implementation Steps" step 4; Phase 3, "Requirements" (bottom inset); plan.md, "Success Criteria"; Phase 7, "Requirements"
- **Flaw:** The boards are 390 px wide at a font scale of 1. Phase 7 checks text at twice the size on four main screens, and Home is one of them. It shows a floating pill 20 dp from each edge, holding four labelled tabs and a labelled centre button. At a font scale of 2 the labels need roughly 450 to 500 dp. The pill has about 372 dp on a 412 dp device. `TextAutoSize.StepBased` steps in sp, so the "32 sp" floor also doubles to about 64 dp per glyph. A VND hero amount such as "₫12.345.678" with Bricolage tabular digits (0.629 em) then needs about 370 dp inside a hero card of about 330 dp. The plan requires "không cắt chữ và không xuống dòng", which together force a cut. The plan's risk (auto-sizing missing from the pinned Compose) does not apply: the API exists. The real risk, overflow at large text, is not addressed. Phase 3 also sets the list's bottom inset as "bằng chiều cao thanh" as if that height were fixed. It grows with the font scale.
- **Failure scenario:** `ScreenGalleryTest` "the four main screens with text at twice the size" records `01-home-large-text` with tab labels cut or overlapping and the hero amount clipped. That breaks the plan's success criterion "chữ cỡ 200% không bị cắt trên bốn màn chính" and Phase 7's "Không chữ nào bị cắt ở cỡ 200%". Phase 7 has 2 days for this, with no design answer.
- **Evidence:** `app/src/test/java/com/dantech/splitvibe/ui/ScreenGalleryTest.kt:184-190` (`RuntimeEnvironment.setFontScale(2f)`, `shot("01-home")`), `:477` (`PHONE = "w412dp-h915dp-xhdpi"`); `app/src/test/screenshots/01-home-large-text.png` exists. `javap`: `foundation-android-1.12.1` has `androidx/compose/foundation/text/TextAutoSize`, and material3 1.5.0-rc01 `Text(..., TextAutoSize, ...)` overloads exist. Plan text: plan.md line 24, "1 px trên bảng ứng với 1 dp"; phase-02 line 78, "các bậc từ 56 xuống 32 sp; không cắt chữ và không xuống dòng"; phase-02 line 100, risk "Cơ chế tự co cỡ chữ không có trong bản Compose đang ghim".
- **Suggested fix:** Specify large-text behaviour now. For example: bar labels drop to icons with labels kept for accessibility, or the bar becomes two rows above a set font scale. Set the hero floor in dp, or allow two lines above a set font scale. Measure the bar's real height for the bottom inset (`onSizeChanged` or `WindowInsets`). Add the large-text Home screenshot to the Phase 2 catalog check instead of finding the problem in Phase 7.

## Finding 5: "Labels stay the same, so tests survive" is false where the interaction model changes
- **Severity:** High
- **Location:** Phase 4, "Key Insights" (list of kept labels), "Requirements / Trình sửa hóa đơn" and "Implementation Steps" steps 7 and 9; Phase 3, step 9
- **Flaw:** The tests depend on structure as well as text. With one editable row at a time, only one item has "Item" and "Amount" fields. `BillLifecycleTest` adds three items and then reads the fields by index, and the e2e helper types into the field of a just-added item without opening its row. Neither test is in the list of things to fix ("thứ tự mới, điểm cuộn, chỗ thêm người"). The kept-label list also leaves out "Add an item", "Where", "Item" and "Amount", which these tests use. "Split a bill" also stops being unique: the centre bar button keeps the label, and the Home empty state, which is exactly what a fresh test install shows, "là lời mời chia hóa đơn đầu tiên". `onNodeWithText` fails when more than one node matches. The open row is stored as an index (`rememberSaveable`), but rows are keyed by id. Deleting or adding an item moves the open state to another item, and one index cannot cover both items and charges.
- **Failure scenario:** `BillLifecycleTest` throws `IndexOutOfBoundsException` at `onAllNodes(hasText("Item") and hasSetTextAction())[1]`. `ManualEntryJourneyTest` and `fillInTheBill` time out on `field("Item")` because the new empty row is closed. - **Evidence:** `app/src/test/java/com/dantech/splitvibe/ui/split/BillLifecycleTest.kt:95-100`; `app/src/androidTest/java/com/dantech/splitvibe/e2e/JourneySteps.kt:79-87`; `onNodeWithText("Split a bill")` at `AppStartupTest.kt:33, 65`, `BackNavigationTest.kt:83, 104`, `androidTest/.../AppLaunchTest.kt:45, 51`, `e2e/*JourneyTest.kt` (4 files); `ui/editor/BillEditorContent.kt:144-145` (`key = "item ${item.id}"`); `core/domain/.../Bill.kt:21-22` (`BillItem.id`). - **Suggested fix:** Store the open row as a saveable item or charge id, not an index. Open a newly added row automatically. List `BillLifecycleTest` and `JourneySteps.fillInTheBill` under the changes Phase 4 must make. Set a rule that exactly one node carries the "Split a bill" text per screen (give the empty-state call to action its own string), or switch the tests to role plus label as Phase 3 does for tabs.

- **Evidence:** `core/designsystem/build.gradle.kts:23-28` (testOptions only set `sv.webTokens`) and `:42` (`testImplementation(libs.junit)` only).
